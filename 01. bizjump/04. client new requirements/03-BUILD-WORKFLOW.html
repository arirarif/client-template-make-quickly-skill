🗄 Where Does Data Live? (Data Model)

This is the foundation. Every piece of data the dashboard shows lives in one of these 4 buckets. Build this first — everything else reads from it.

👤 1. User Profile (ACF fields)

Stored in: WordPress user_meta table
  • Business Name
  • Entity Type (LLC / Corp / etc.)
  • State
  • Formation Date
  • EIN Number
  • Registered Agent
  • Filing Status (admin-controlled)
  • EIN Status (admin-controlled)

🛒 2. Products & Orders (WooCommerce)

Stored in: Woo's products & orders tables
  • Formation Package (subscription product)
  • Registered Agent (subscription)
  • EIN Filing (one-time service)
  • Add-ons: Operating Agreement, Bank Setup, Social Media, etc.
  • Customer's active services = their orders

📅 3. Custom Post Types (CPTs)

Stored in: WP posts table
  • compliance_item — deadlines per user (Annual Report, Tax, etc.)
  • action_task — checklist items (Apply for EIN, Open bank, etc.)
  • notification — log of in-app alerts per user

📁 4. Plugin-Owned Data

Stored in: each plugin's tables
  • Documents → WP File Download (per-user folders)
  • Tickets / chat → Fluent Support tables
  • Email automations → FluentCRM tables
  • Calendar events → The Events Calendar
✅ Why this matters Once these 4 buckets exist, every screen in the dashboard is just "read from bucket X and display". No screen needs new data — it just presents data that already lives in the system.

💧 Data Flow — How Data Moves From Database to Screen

A concrete example: customer logs in and sees their Filing Status. Here's every step that happens.
1
Admin marks a status (one time)

Your team opens WP Admin → Users → Edit user → ACF field "Filing Status" → selects Filed with State. Saved to wp_usermeta.

2
Customer logs into their account

WordPress authenticates them → loads /my-account/dashboard/

3
The dashboard template runs PHP

Custom template calls get_field('filing_status', 'user_' . $user_id) → returns "Filed with State"

4
HTML renders

Template outputs the status pill: Filed with State + progress bar at 66%

5
FluentCRM fires automation (optional)

If status changed since last visit, an email "Your business has been filed!" is sent. Notification CPT row created → shown in 🔔 bell icon.

📝 Same pattern works for everything Documents, services, compliance items, action tasks — all follow this exact loop: admin updates → DB stores → customer page reads → HTML renders. You build the loop once, reuse it 7 times for the 7 sections.

⚖️ Frontend vs Backend — Who Does What?

A common confusion. Here's the clean split.

📺 FRONTEND (Customer side)

What the customer sees & clicks in their browser
  • Custom My Account pages (built with PHP templates + HTML/CSS)
  • Sidebar navigation, top bar, page layouts
  • READS data from the database via WP functions
  • NEVER directly writes critical data (filing status, etc.)
  • Customer can: edit profile, upload docs, message support, mark action tasks done, view services, buy add-ons
  • Built with: PHP templates, CSS, optional JavaScript for interactivity

⚙️ BACKEND (Admin / Server side)

What runs invisibly + WP Admin where your team works
  • Database (MySQL) stores everything
  • WP-Admin where BizJump team manages users, products, status
  • Plugins do their work (Woo processes orders, FluentCRM sends emails, Fluent Support routes tickets)
  • Cron jobs run scheduled reminders
  • Hooks/triggers fire when things change (status update → email)
  • Admin can: edit any user's data, mark filing status, upload docs, reply to tickets, view all customers
📌 Where does data come from? — The simple answer Customer creates account → some fields are entered by them (name, email, business name during signup form). BizJump admin fills the rest manually as filings progress (Filing Status, EIN, document uploads). Plugins generate data automatically (Woo creates orders, Fluent Support creates tickets). Everything lands in the same database. Frontend reads from it.

❓ Common Confusions — Cleared Up

Things that trip people up on builds like this.

"Where does the customer's business data come from?"

Three sources: (1) the customer types it during checkout (business name, entity type — captured via Gravity Form on the order page); (2) BizJump admin fills it in as filings happen (Filing Status, EIN); (3) plugins generate it automatically (Woo creates the order, FluentCRM logs the email). All of it ends up in the WP database.

"Do I build frontend or backend first?"

Backend first, always. Build the data model (Phase 1) and admin tools (Phase 2) before any customer-facing screen. The frontend is just a "view" of backend data — without backend data to show, frontend has nothing to render.

"How do customers see real-time updates?"

They don't, technically. When admin updates a status, it saves to the DB. The next time the customer loads their dashboard, the new status shows. For "live" feel, FluentCRM sends them an email + creates an in-app notification, so they get notified to come check.

"What if the client wants something not in the spec?"

Reference back to the FEASIBILITY-ANALYSIS.html doc — anything outside the 92% scope is a separate change request. Document it, scope it, price it. Don't accept "just one more thing" verbally.

"Why is Dashboard Home built last?"

Because it shows summaries of every other section. If Compliance shows "3 deadlines coming up" on the home page, that data only exists once the Compliance section is built. Build the parts first, then the dashboard that aggregates them.

"Where do I put my custom code?"

Either a child theme (for template overrides) or a custom plugin (for functionality). Don't edit core WordPress, WoodMart, or any plugin files directly — updates will wipe your changes. The "Action Center" mini-plugin should be its own custom plugin folder.
