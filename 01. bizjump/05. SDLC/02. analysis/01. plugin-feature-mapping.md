# Phase 2 — Analysis: Plugin → Feature Mapping

> **Goal:** For every requirement section, decide: KEEP the plugin / EXTRACT functionality into our custom plugin / build CUSTOM from scratch.
> **Approach:** No over-engineering. If a plugin already does the job well and the client UX isn't hurt by it, we keep it. If we'd be hiding 80% of a plugin's UI just to use 20% of its logic, we extract. If no plugin does the thing (Action Center), we build it.

---

## 1. Decision legend

| Marker | Meaning |
|---|---|
| **KEEP** | Use the plugin as-is. Configure it, don't replace it. |
| **EXTRACT** | Study the plugin's logic and rebuild a stripped-down version inside our custom plugin. Original plugin gets uninstalled. |
| **CUSTOM** | No plugin source — we design and build from scratch. |
| **WRAP** | Keep the plugin running but build our own UI on top of its API/data. |

---

## 3. Section-by-section mapping

### §1 Dashboard Home
**Decision: CUSTOM**
Composes data from ACF (business fields), WooCommerce (orders/services), our Action Center module (checklist progress), and Notifications. No plugin does this composition. We build the layout as a WC My Account endpoint.

---

### §2 Document Hub
**Source plugin: WP File Download Pro**
**Decision: EXTRACT**

Why extract:
- Plugin's strength is the admin file manager UI and folder tree — neither of which fits our spec.
- We need: per-user folder, status tags (Ready/Pending/Processing), a clean table, upload/download buttons. That's ~15% of the plugin.
- We avoid loading WP File Download's heavy admin assets on every page.

What to study before building:
- How they scope files per user (capability checks, folder ownership)
- How they generate secure download URLs (nonces, signed URLs)
- Upload handling (mime type validation, size limits)

What we drop:
- Cloud sync (Dropbox/GDrive/S3) — not in spec
- Frontend file manager — not in spec
- Categories/tags beyond our 3 statuses — not in spec
- Shortcodes — we render our own template

---

### §3 Compliance Center
**Source plugin: The Events Calendar Pro**
**Decision: EXTRACT**

Why extract:
- Plugin is built for public events, not personal compliance deadlines. Most of its UI (event single page, RSVP, venues, organizers) is irrelevant.
- We need: monthly grid view, color-coded events per user, recurring events for annual filings, list of upcoming deadlines. ~10% of the plugin.

What to study before building:
- Recurring event rule engine (RRULE / iCal logic)
- Their CPT model + how they query date ranges efficiently
- Their month/calendar render approach (we'll likely use FullCalendar.js anyway)

What we drop:
- Public event archive
- Tickets, RSVPs, venues, organizers
- Multiple views (week/day/photo) — month + list only
- Premium views (map/photo/week) — not needed

---

### §4 Service Management
**Source plugin: WooCommerce Subscriptions**
**Decision: KEEP** (don't extract)

Why keep:
- Subscriptions plugin handles recurring billing, renewal logic, payment retries, status transitions — all of this is risky to rebuild.
- Touches PCI/payment surface. Not worth the risk for one-off client work.
- Customer-facing UI on subscriptions is hidden anyway — we'll WRAP with our own My Account section that queries the subscription API.

Action: configure once, build our own service-cards UI on top of `wcs_get_users_subscriptions()`.

---

### §5 Action Center ⭐
**Source plugin: None** (this is the differentiator)
**Decision: CUSTOM**

Why custom:
- No plugin provides a 3-tab checklist with per-task progress, expand-for-instructions, "View Details" deep link, and "Mark Complete" persistence per user.
- Closest analog (GamiPress) is overkill and adds badges/points the client said are not wanted.

Build approach:
- Custom CPT: `bizjump_task` (title, instructions, category: setup/growth/compliance)
- User meta: completion state per task per user
- Simple template + AJAX toggle for checkboxes
- Admin: list table to manage tasks

---

### §6 Communication Hub
**Source plugin: Fluent Support Pro**
**Decision: WRAP**

Why wrap (not extract, not keep-as-is):
- Fluent Support's ticket engine is solid (threading, attachments, agent assignment, SLA, internal notes). Rebuilding would take weeks.
- BUT its customer portal UI doesn't match our spec — we want the layout from `image16.png` (conversation list + chat thread, not a ticket list).
- So: keep Fluent Support running for the engine, build our own customer-facing template that calls Fluent Support's REST API.

Admin side: BizJump team uses Fluent Support's native admin (it's good). No need to consolidate that.

---

### §7 Business Profile
**Source plugin: ACF Pro + Gravity Forms**
**Decision: CUSTOM** (small)

Why custom:
- ACF already stores the data (kept).
- Gravity Forms is overkill for a 7-field edit form. Loading the full GF asset bundle for one form is wasteful.
- Build a simple AJAX form with sanitization → updates ACF user meta. ~150 lines of PHP.

Gravity Forms can still be installed for any other intake forms BizJump uses elsewhere. But not for this section.

---

### §8 Sidebar Menu
**Source plugin: YITH Customize My Account Pro**
**Decision: EXTRACT**

Why extract:
- We only need 8 hardcoded menu items in a fixed order. YITH's drag-drop builder UI is 90% of the plugin and we won't expose it.
- Replacing it = ~50 lines using `woocommerce_account_menu_items` filter + custom endpoints via `add_rewrite_endpoint`.

What to study:
- How they register endpoints cleanly (some plugins forget to flush rewrite rules)
- Their permalink structure

---

### §9 Notifications System
**Source plugin: Notification (BracketSpace) Pro**
**Decision: EXTRACT**

Why extract:
- We need 5 fixed triggers (filing change, EIN milestone, deadline, message, document). Bracketspace's value is a generic trigger/recipient/carrier engine — too abstract for our 5 hardcoded events.
- In-app bell with unread count is ~200 lines: custom table `bizjump_notifications`, REST endpoint, header template part.

What to study:
- Their action-hook → notification pipeline (clean separation of concerns)
- How they batch deliveries

What we drop:
- Triggers UI builder — we hardcode 5
- Multiple carriers (Slack, webhook, etc.) — only in-app + email
- Merge tags engine — we use simple sprintf

---

### §10 Empty States
**Decision: CUSTOM** (template strings, not even worth a section)
3 strings hardcoded into the section templates.

WoodMart already owns this. We add the bell icon as a header element via WoodMart's hook.

### §12 Support Access
**Decision: CUSTOM** (trivial)
A persistent button rendered by our plugin into a global hook. Opens the Communication Hub or external Fluent Support form.

## 4. Cross-cutting: CRM & Email

**Plugin: FluentCRM Pro**
**Decision: KEEP**

Why keep:
- FluentCRM's email sequencer, contact tags, automation flows are battle-tested.
- We trigger automations from our plugin (e.g. on filing-status-change → trigger CRM tag → CRM sends email sequence). Clean separation.
- Replacing this = rebuilding an email engine. No.

Our plugin emits events; FluentCRM listens and fires emails.

**Final plugin footprint after consolidation:**

Active plugins on the live site:
1. WooCommerce (free) — orders/payments
2. WooCommerce Subscriptions — recurring billing
3. ACF Pro — data fields
4. FluentCRM — email automations
5. Fluent Support — ticket engine (UI hidden, API used)
6. FluentSMTP — email delivery
7. **`bizjump-core` (our plugin)** — everything customer-facing + admin consolidation

Plugins removed (functionality folded into `bizjump-core`):
- WP File Download Pro
- The Events Calendar Pro
- YITH Customize My Account Pro
- Notification (BracketSpace) Pro

Result: **7 active plugins** instead of 11, with one unified customer dashboard and one unified admin section in `bizjump-core` for managing documents, compliance events, action tasks, notifications, and dashboard config. The kept plugins (Woo Subs, Fluent Support, FluentCRM) keep their own admin since they're complex enough that consolidating them would be a net loss.

## 6. Risks flagged for design phase

1. **REST API surface for Fluent Support** — verify our wrap approach works before committing. If their API is incomplete, fall back to direct DB queries or escalate to KEEP.
2. **WooCommerce Subscriptions hooks** — confirm hook stability across the WC version we'll target. Known to break on major WC upgrades.
3. **Recurring compliance events** — do we need RRULE parsing or can we get away with "yearly on date X" / "quarterly" presets? Confirm in design.
4. **Per-user document storage path** — must be outside web root or properly access-controlled. Document download URLs must require auth.
