# Phase 3 — Design: Architecture

> **Goal:** Describe the structure of the `bizjump-core` plugin and how it sits inside the WordPress + WooCommerce stack.
> **Principle:** Build for what the spec asks for, nothing more. No abstraction layers we don't currently need. No "future flexibility" code.

---

## 1. High-level shape

One custom plugin: **`bizjump-core`**.
Inside it, one folder per feature module. Modules share a small core (bootstrap, autoloader, REST registration, asset enqueue helper). Nothing else is shared until we hit the second copy-paste — *then* we extract, not before.

```
bizjump-core/
├── bizjump-core.php          # Plugin header + bootstrap (50 lines)
├── core/
│   ├── class-bootstrap.php   # Loads modules
│   ├── class-rest.php        # REST namespace registration
│   ├── class-assets.php      # Single CSS/JS bundle helper
│   └── class-capabilities.php
├── modules/
│   ├── dashboard/            # §1 Dashboard Home
│   ├── documents/            # §2 Document Hub (extracted from WP File Download)
│   ├── compliance/           # §3 Compliance Center (extracted from Events Calendar)
│   ├── services/             # §4 Service Mgmt (wraps WC Subscriptions)
│   ├── action-center/        # §5 Action Plan (custom)
│   ├── messages/             # §6 Comm Hub (wraps Fluent Support)
│   ├── profile/              # §7 Business Profile
│   ├── sidebar/              # §8 Sidebar nav (extracted from YITH)
│   ├── notifications/        # §9 In-app + email triggers
│   └── support-button/       # §12 Floating support button
├── admin/
│   ├── class-admin-menu.php  # Single "BizJump" top-level menu
│   ├── views/                # Tab views (one per module that needs admin)
│   └── class-settings.php
├── templates/
│   ├── my-account/           # WC My Account template overrides
│   └── parts/                # Shared template partials (status pill, table, etc.)
├── assets/
│   ├── dist/
│   │   ├── bizjump.css       # ONE bundled CSS for whole dashboard
│   │   └── bizjump.js        # ONE bundled JS
│   └── src/                  # SCSS / JS source (build with npm script)
└── languages/                # .pot file (English only, no i18n active)
```

Every module is a folder containing the same files: `class-{module}.php` (entry), optional `class-{module}-rest.php`, `class-{module}-admin.php`, `templates/`, and `assets/` if anything is module-specific. Predictable. Easy to delete or replace one module without touching others.

---

## 2. Module entry pattern

Every module has the same shape:

```php
namespace BizJump\Modules\Documents;

class Documents {
    public function __construct() {
        add_action( 'init',                    [ $this, 'register' ] );
        add_action( 'rest_api_init',           [ $this, 'register_rest' ] );
        add_action( 'woocommerce_account_documents_endpoint', [ $this, 'render' ] );
    }
    // register(), register_rest(), render() ...
}
```

`Bootstrap` loads modules in a fixed order. No service container, no DI. WordPress already provides the hook system — adding another layer is the over-engineering we agreed to skip.

## 3. Data layer

Three storage mechanisms. Pick the right one per data type:

| Data | Storage | Reason |
|---|---|---|
| Business profile fields (name, entity, state, EIN, agent, formation date) | **ACF user meta** | Already the spec; ACF Pro is foundation |
| Subscription/order data | **WooCommerce native** | Already there, never duplicate |
| Action Center tasks (template tasks) | **CPT `bizjump_task`** | Edited by admin |
| Action Center per-user completion state | **User meta `bizjump_task_completion`** (single JSON blob) | Sparse, bounded, no need for a table |
| Documents | **Custom table `wp_bizjump_documents`** (file path, owner_id, status, type, uploaded_at) | High row count expected, status updates frequent — meta is wrong tool |
| Compliance events | **Custom table `wp_bizjump_compliance_events`** (owner_id, due_date, type, status, recurrence_rule) | Date queries need indexes; CPT date_query is too slow |
| In-app notifications | **Custom table `wp_bizjump_notifications`** (user_id, type, payload JSON, read_at, created_at) | Append-only, very high row count, deletes by age |
| Plugin settings | **WP option `bizjump_settings`** (single serialized array) | Small, infrequently changed |

Three custom tables total. Schema goes in `core/class-installer.php`, runs on plugin activation via `dbDelta()`.

**No ORM.** `$wpdb->prepare()` everywhere. Every query reviewed for SQL injection.

## 4. URL & routing

Customer dashboard lives at `/my-account/{section}/` using WooCommerce endpoints:

| URL | WC endpoint | Module |
|---|---|---|
| `/my-account/` | `dashboard` (default) | dashboard |
| `/my-account/documents/` | `documents` | documents |
| `/my-account/compliance/` | `compliance` | compliance |
| `/my-account/services/` | `services` | services |
| `/my-account/action-plan/` | `action-plan` | action-center |
| `/my-account/messages/` | `messages` | messages |
| `/my-account/profile/` | `profile` | profile |

Endpoints registered via `add_rewrite_endpoint()` in `core/class-bootstrap.php`. Flushed on plugin activation only — never on every page load.

## 5. REST API

Single namespace: `bizjump/v1`.

| Endpoint | Method | Purpose |
|---|---|---|
| `/documents` | GET | List user's documents |
| `/documents/upload` | POST | Upload new document |
| `/documents/{id}/download` | GET | Signed download URL |
| `/compliance/events` | GET | List user's events (date range) |
| `/action-plan/tasks` | GET | List tasks with completion state |
| `/action-plan/tasks/{id}/toggle` | POST | Mark task complete/incomplete |
| `/messages/threads` | GET | Fluent Support wrapper |
| `/messages/threads/{id}/reply` | POST | Fluent Support wrapper |
| `/profile` | GET / POST | Read/update ACF user fields |
| `/notifications` | GET | List unread + recent |
| `/notifications/{id}/read` | POST | Mark read |

All endpoints require `is_user_logged_in()` + capability check. Per-resource ownership check (e.g. document `owner_id === current_user_id`) before any read or write.

Frontend JS calls these via `wp.apiFetch` with nonce.

## 6. Admin panel structure

**One top-level menu: "BizJump"**

```
BizJump
├── Dashboard      (admin overview — quick stats)
├── Documents      (review uploaded docs, set status)
├── Compliance     (manage event templates + per-user events)
├── Action Tasks   (CRUD task templates)
├── Notifications  (logs + manual send)
└── Settings       (business meta defaults, email triggers, integrations)
```

Each is a submenu page rendered by the matching module's `class-{module}-admin.php`. WooCommerce, FluentCRM, Fluent Support keep their own menus — we don't try to swallow them.

UI built with native WP admin styles (`.wrap`, `.wp-list-table`, `WP_List_Table` class). No React, no custom framework. Saves bundle weight and the client's hosting can handle it.

## 7. Hook strategy & namespacing

- Hook prefix: `bizjump_`
- Option keys: `bizjump_*`
- Custom tables: `{$wpdb->prefix}bizjump_*`
- CSS classes: `.bizjump-*`
- JS globals: single object `window.BizJump`
- Constants: `BIZJUMP_VERSION`, `BIZJUMP_PATH`, `BIZJUMP_URL`

Events emitted (for FluentCRM and downstream listeners):
- `bizjump_business_filing_status_changed` ($user_id, $old, $new)
- `bizjump_ein_status_changed` ($user_id, $old, $new)
- `bizjump_document_uploaded` ($user_id, $document_id)
- `bizjump_compliance_event_due_soon` ($user_id, $event_id, $days_remaining)
- `bizjump_message_received` ($user_id, $message_id)

FluentCRM hooks into these via Uncanny Automator OR direct `add_action()` in a small mu-plugin. We don't manage FluentCRM automations from inside our plugin — keep the boundary clean.

---

## 8. Asset strategy

- One CSS bundle, one JS bundle, both built from `assets/src/`.
- Loaded only on dashboard pages (check `is_account_page()`).
- Loaded once globally, NOT per module — small enough that splitting hurts more than it helps.
- No jQuery dependency (vanilla JS + `wp.apiFetch`).
- CSS uses BEM with `.bizjump-` prefix to avoid theme conflicts.

---

## 9. Security checklist

Built into the design, not bolted on:

- [ ] Every REST endpoint: `is_user_logged_in()` + nonce + capability
- [ ] Per-resource ownership check on every read and write
- [ ] Document files stored outside web root (`wp-content/uploads/bizjump-private/`) with `.htaccess` deny-all
- [ ] Document downloads served via PHP `readfile()` with signed nonce, not direct URL
- [ ] All `$wpdb` queries use `prepare()`
- [ ] All user input sanitized (`sanitize_text_field`, `sanitize_email`, `wp_kses_post` for messages)
- [ ] All output escaped (`esc_html`, `esc_attr`, `esc_url`)
- [ ] File uploads: mime type + extension whitelist (PDF, DOCX, JPG, PNG only)
- [ ] CSRF: WP nonces on every form and AJAX call

## 10. Things we are deliberately NOT building

(Listed so future-me doesn't think they were forgotten.)

- DI container / service locator
- Event dispatcher abstraction (WP hooks are fine)
- Multi-tenant separation (one site, one tenant)
- Plugin update server / licensing
- Test framework setup (manual testing per Phase 5)
- Migration system (one schema, one activation hook)
- Internationalization beyond the .pot file
- Settings export/import
- Audit log (unless client asks in v2)
- Custom block editor blocks
- WP-CLI commands

If any of these become needed, that's a new ticket — not Phase 1 scope.

3. Action Center tasks — same for every customer, or per-state / per-entity-type variations?
