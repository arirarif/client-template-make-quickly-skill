## 2. PHASE A — the light re-skin (this round's real deliverable)

> ## ✅ PHASE A DONE — shipped as v3.20.2 on 2026-09-08
>
> Measured, built, deployed and verified in the browser. Details in §9 below.
> Steps 1-6 are kept as written because the method is worth re-running.

### Step 1 · Measure the benchmark *first* (30 min)

Two measurements, same method used on Arabian Oud on 16/08:

1. **noorfestivities.com** (his live site — his stated benchmark). Record: painted-surface % by
   colour bucket, and the hex list. **Also record any colour that is not in the 2023 charter.**
2. **noor.futurecards.nl** (our staging, current v3.19.0). Same numbers.

Write both into this file as a table. This turns "too dark" into a number you can hit and later
prove you hit — which is the only way to close a subjective complaint for good.

**Target: ≥ 85 % white/near-white, ≤ 5 % brown, and measurably lighter than his own site.**

### Step 2 · Build it behind a flag, not on a duplicate site

Do **not** clone staging. Add one stylesheet, `assets/css/noor-light.css`, enqueued after
`noor-woocommerce`, activated by a `noor_theme=light` flag — the same pattern `inc/region.php`
already uses for `?noor_switch=`.

⚠️ **Cache trap — this project has already been bitten by exactly this.** In early August, hiding
rental blocks *server-side* poisoned the LiteSpeed cache: the France version of the page got served
to Réunion visitors and rentals vanished for everyone. A server-rendered light/dark switch has the
**identical** failure mode.

Two safe options, in order of preference:

- **Preferred — keep the flag admin-only.** Gate it on `current_user_can('manage_options')` so
  anonymous (cached) traffic never sees a variant. Once the light version is approved it becomes the
  **only** version, which is cache-safe by construction because every visitor gets the same HTML.
- Fallback, only if he insists on comparing two live links: do the switch **client-side** (cookie →
  class on `<html>` via a small inline script in `header.php`), never in PHP output.

### Step 3 · The token changes

`noor-light.css` overrides `:root` and the ten surfaces above. Proposed mapping:

| Token / surface | From | To |
|---|---|---|
| `--noor-bg` / `--nfw-bg` | `#EDE5DE` | `#FFFFFF` |
| `--noor-card` / `--nfw-card` | `#FAF6F1` | `#FFFFFF` (borders do the separating, not fills) |
| `--noor-band` | `#EED2AE` | keep the hex, **use it far less** — bands only, never full sections |
| `--noor-border` | `#DCC7AC` | `#EADFD2` (lighter, so borders can replace fills) |
| Hero base + overlay | espresso + `.55` | image on white, scrim `rgba(46,26,13,.30)` → transparent → `#fff` |
| Footer | `#2E1A0D` | `#EED2AE` (Creamy Beige) with `#2E1A0D` text |
| Marquee | `#7A3512` | `#FFFFFF` with a 1px `--noor-border` rule, mocha text |
| Category overlay | `.25` → `.8` | `.15` → `.55`, or caption moved below the tile on white |
| Rental banner overlay | coral `.94` | coral `.55`, or a white card with a coral left border |
| `.noor-band-gradient` | mocha gradient | `#FFFFFF` card, mocha heading + mocha button |
| Mocha `#96421A` | used as fill **and** accent | **accent only** — buttons, links, prices, kickers, active states, icons |

**No new colours.** Every value above is either a charter colour, white, or a derived tint of one —
which is literally what he asked for ("uniquement les couleurs de mon branding").

### Step 4 · Contrast gates (check while building, not after)

Computed from the charter hexes:

- `#96421A` on white = **6.8:1** → passes AA for body text, AAA for large. Safe everywhere.
- White text on a `#96421A` button = **6.8:1** → AA pass. Buttons keep white labels.
- `#2E1A0D` on `#EED2AE` footer ≈ **12:1** → comfortable.
- ⚠️ `#C68053` (Spiced Coral) on white = **3.0:1** → **fails AA for normal text.** Coral stays
  decorative — borders, chips, large display text only. Never body copy, never small labels.
  (This matches the existing rule in `BRANDING.md`.)

### Step 5 · Keep the serif

Arabian Oud uses one sans for everything. **Do not copy that.** Ragara / Playfair on headings is
what stops Noorfestivities looking like a generic template — already argued to him on 16/08 and he
did not object. Light ≠ plain.

### Step 6 · Ship

1. Bump **both** `NOOR_VERSION` in `functions.php` **and** `Version:` in `style.css` → **v3.20.0**
   (minor bump: new stylesheet + visual change, no breaking API).
2. `python scratchpad/phplint.py 07-final-build/noor-child/inc/*.php`
3. `python scratchpad/build-zip.py` — **not** `Compress-Archive`.

5. Verify live version in the browser console from the enqueued `noor.css` `ver=` query arg.
6. **Re-run the Step 1 measurement on the new build** and confirm the ≥ 85 % target.
7. Screenshot home / shop / product / cart, light vs dark, for the client message.

### Step 7 · Then flip the default

Once you have looked at it and the numbers hit: make light the default for everyone, keep the flag
as the revert switch. Send him **one** link, not two — he answers in single words; "here is the site,

## 4. PHASE C — the product catalogue pipeline

He asked *"il faut que je fasse un export ?"* — **the answer is yes**, and give him the click path,
not a description.

1. **Verify first** (do not assume): is noorfestivities.com actually WooCommerce? If yes →

2. Import target: **WooCommerce's native CSV importer**, not `08 products/svpi-importer`. The SVPI

3. **Images from his Drive folder:** download → strip EXIF → resize to a single ratio → WebP.

   the import on 3 rows first.

Full-page grid sampling (48 x 30 points per viewport band, `elementFromPoint`
walked up to the first painting ancestor), homepage, 1536x722, WP admin bar
excluded:

| painted surface | his site | staging v3.19.0 | **staging light v3.20.2** |
|---|---|---|---|
| pure `#FFFFFF` | 56.2 % | **0.0 %** | **79.3 %** |
| warm off-whites (`#EDE5DE`, `#FAF6F1`) | 0.0 % | 58.9 % | 0.3 % |
| Creamy Beige `#EED2AE` | 9.4 % | 12.2 % | 1.0 % |
| brown fill | 6.8 % (`#A05530`) | 0.5 % (`#96421A`) | 0.2 % |
| espresso slabs | 0.0 % | 4.3 % | 0.08 % |
| mocha gradient band | 0.0 % | 8.8 % | 0.0 % |
| photography | 27.2 % | 12.0 % | 19.0 % |
| **light share of non-image surface** | **77 %** | 69 % | **98.2 %** |

**This overturned the plan's own reading of POINT 0.** Two findings:

1. **He uses more brown than we did** — 6.8 % against 0.5 %. "Je veux pas le
   marron" therefore cannot mean *remove the colour*; taken literally it would
   have stripped a colour he himself uses fourteen times more of than we did.
   Reading (A) in §0 is confirmed by measurement, not by argument.
2. **We had literally zero pure white.** Not one sample in 10,080. Every
   surface on the site was a warm tint. That — not the brown — is what his eye
   was comparing against 56 % brilliant white.

His brown is also `#A05530`, not the charter's `#96421A`. Close, but it is a
non-charter colour, which is the conflict §0 said to check for. It is not worth
raising: he asked for charter colours, and `#96421A` is the charter.

### 9.2 What his homepage actually looks like (this changed the hero)

Text left on white, one large product photo right, brown script headline, cream
header, brown button. **The colour comes entirely from pastel product
photography, not from fills.** His hero is not a dark photo with text on top —
it is text *beside* a photo.

So the hero was rebuilt as a two-column grid instead of merely lightening the
overlay: `.nfw-hero__img` stops being an absolute full-bleed layer and becomes
the right column, `.nfw-hero__overlay` is removed. Contrast is then structural
(espresso on white) rather than dependent on how light the photograph is. Same
markup, CSS only — no widget PHP was touched.

### 9.3 The cascade trap — four colours were not in the theme at all

`html.noor-light` is (0,2,1). Elementor writes editor-set colours into
`post-16.css` as `.elementor-16 .elementor-element.elementor-element-<id> .nfw-marquee`
— (0,3,1), loaded *after* the theme. So the first deploy changed nothing
visible on the marquee, the rental banner, or the hero's emphasised word.

Found by enumerating every `post-*.css` rule touching a `.nfw-`/`.noor-` class.
Four hits, all now `!important`:

| selector | was | why it mattered |
|---|---|---|
| `.nfw-marquee` | `#7A3512` | full-width brown band under the header |
| `.nfw-marquee__item` | `#EDE5DE` | its text, once the band went white |
| `.nfw-hero__title em` | `#EED2AE` | **beige on white = 1.4:1** — "Chaque" was invisible |
| `.nfw-rental__overlay` | coral .94 | near-opaque wash over a 300px block |

Plus a whole Elementor **section** carrying a `#FAF6F1` fill across 14 % of the
page. Section fills are now cleared wholesale (`background-color` only, so
background *images* survive).

⚠️ **Re-run that scan after any Elementor page edit** — the widget ids change
when a page is rebuilt, and any colour typed into the editor silently outranks
this stylesheet.

Method note: the override was tested by injecting it as the **first** child of
`<head>`, not the last, to prove `!important` wins on merit rather than on load
order.

### 9.4 Two things the naive token swap would have broken

- `--noor-bg` was doing double duty as the page background **and** as the hover
  fill on menu items, header icons and the drawer, plus the free-shipping
  progress track. Turning it white would have made all five invisible. They are
  re-pointed at a new `--noor-tint` (`#F7F1EA`).
- The footer logo is `logo-ivory.png`, chosen because the footer was espresso.
  On Creamy Beige it nearly vanished. `noor_footer_logo_url()` now returns
  `logo-mocha.png` under the light skin; an explicit Customizer choice still
  wins in both skins.

### 9.5 Cache safety — verified, not assumed

`NOOR_LIGHT_DEFAULT` is **`false`**. The `?noor_theme=` parameter is gated on
`current_user_can('manage_options')`.

Verified by fetching with `credentials:'omit'`:

- anonymous, plain URL → no `noor-light` class
- anonymous, **explicitly** `?noor_theme=light` → still no `noor-light` class
- logged-in admin → light skin

Anonymous traffic therefore has exactly one variant and cannot poison the
LiteSpeed cache the way the August region bug did. Flipping the constant to
`true` moves everyone at once — still one variant, still safe.

### 9.6 Deploy notes (recipe corrections)

- **`#themeinstallform` no longer exists** in this WordPress version — the

- The theme replace purges LiteSpeed itself ("Purged all caches successfully").
- After the replace, **reload before judging the page** — the tab keeps the

### 10.1 Bug found and fixed — the price was off-brand and failed AA

Not caused by the light skin; it was wrong in **both** skins and merely became
obvious on white.

WooCommerce's **own** stylesheet paints the price and stock line `#958E09`, an
olive derived from its default accent (`--woocommerce` is still `#720eec` on
this install — never branded). `noor.css:373` already declares the intended
espresso, and loses: core's selector is

```
.woocommerce:where(body:not(.woocommerce-uses-block-theme)) div.product p.price
```

`:where()` contributes zero specificity, so that is (0,2,2) against our (0,2,0).

Measured before: **3.41:1** — below AA for the stock line at 14.7px.
After: price **16.5:1**, in-stock green **5.4:1**.

Fixed in `assets/css/woocommerce.css` (not the light skin — it applies to both)
by outranking core at (0,4,2) / (0,3,3). **No `!important` was needed**, and
that was verified the same way as the Elementor overrides: injected as the first
child of `<head>`, where it still won.
